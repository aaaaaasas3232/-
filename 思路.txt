## 0. 一句话总览

**所有「人设」都从「单条记录」升级为「原型 + 实例 + 引用关系」的三层结构**：

- **原型（Template）**：系统内置或用户新建的「模板」。例如「用户模板」「AI 模板」「世界观模板」。
- **实例（Record）**：基于原型创建出来的具体角色 / 世界 / 阵营 / 城市，例如「user0」「绒城」「A 城」「小张」。
- **关系（Relation）**：实例之间的引用，例如「小张居住在绒城」「AI 接入微博内容」「购物 App 读取当前世界观」。

后续每个新 App 不直接存自己的人设数据，而是**通过统一的 settings-sdk 读取/写入**这些原型 + 实例 + 关系。

### 0.1 AI 上下文注入管道（本文主线）

### 0.2 ★ 实体档案 Profile：详细 / 简略 双形态（横切概念）

> **本节是横切概念**，适用于 user / ai / world **三种实体**。它是"用户可以隐藏复杂字段"的官方机制。

#### 0.2.1 核心想法

每个实体的字段**不是平等的**——有些是必须填的"骨架"，有些是锦上添花的"细节"。用户可以**在两种模式之间随时切换**：

| 模式 | 别名 | 字段可见性 | 适用人群 |
|---|---|---|---|
| `detailed`（详细） | "完整档案" | 显示**所有**字段（包括可隐藏字段） | 愿意花时间调教人设的人 |
| `minimal`（简略） | "问卷必填" / "轻量档案" | **只显示必填字段** + 已写过的字段 | 不想折腾、想要快速上手的人 |

#### 0.2.2 每个字段的标记

字段级粒度，**与字段所在的实体表绑定**（不存到全局表里）。每个字段都可以带三个标记：

```text
{
  fieldKey: 'personaRef',    // 字段名
  visibility: 'required' | 'optional' | 'advanced',
  //              ↑ 必须填     ↑ 可选    ↑ 进详细模式才显示
  hiddenInMinimal: true,     // 显式声明：简略模式隐藏（=可选的高级字段专用）
}
```

| 标记 | 含义 | 必填？ | 详细模式 | 简略模式 |
|---|---|---|---|---|
| `required` | 必须填 | ✅ 是 | 显示且必填 | 显示且必填 |
| `optional` | 可选 | ❌ 否 | 显示 | 显示 |
| `advanced` | 高级 | ❌ 否 | 显示 | **隐藏** |

#### 0.2.3 切换模式的语义

**用户从详细切到简略**：
- 字段**不删**，只是从 UI 上隐藏。
- 已经填过的 `advanced` 字段**值保留**。
- 下次切回详细，所有值原样回来。

**用户从简略切到详细**：
- 所有 `advanced` 字段从数据库里**重新可见**。

**写入时**：无论当前什么模式，写入**永远生效**（不受模式约束）——模式只决定**UI 上看不看得到这个字段**，不影响数据。

#### 0.2.4 在 §1 / §2 / §3 字段表里的标记约定

每个实体的字段表（§1.2 / §2.1 / §3.1）会给每个字段加一个"显示模式"列，用简写符号：

| 符号 | 含义 |
|---|---|
| 🔴 `R` | required —— 详细 / 简略都必填 |
| 🟡 `O` | optional —— 详细 / 简略都可选 |
| 🟣 `A` | advanced —— 仅详细模式可见 |

#### 0.2.5 settings-sdk API

```text
// 读实例时按 profile 过滤字段（不删数据，只删视图）
settings-sdk.profile.getInstance(entityType, id, { level: 'minimal' | 'detailed' })

// 读所有实例的字段清单（用于设置 UI 生成表单）
settings-sdk.profile.getFieldSchema(entityType)
// → [{ fieldKey: 'name', visibility: 'required', label: '...', ... }, ...]

// 切换模式（全局开关 / 也可以按实体切换）
settings-sdk.profile.setLevel('minimal')              // 全局
settings-sdk.profile.setLevelFor('ai0', 'detailed')  // 仅 AI 实例
```

**默认模式**：第一版默认 `minimal`（想用就开简单；想调细节自己切）。后续看反馈决定要不要让首次启动弹个"详细 / 简略"选择。

#### 0.2.6 对 §5.3 组装顺序的影响

`feed.collectForAi(ai0)` 输出的"AI 上下文片段"也要按 profile 过滤：

- `detailed` 模式 → 给 AI 喂完整的人设（personality rules / detailed rules / 多条 sentimentMap notes 全部注入）
- `minimal` 模式 → 只喂 summary + 关键 sentimentMap；`advanced` 字段不进上下文

详见 §5.3 组装顺序的 ① 步骤。

## 1. 用户（人设 / 资产 / 社媒）

### 1.1 用户是「原型 + 实例」

- **原型**：`userTemplate`（系统自带一份「通用用户模板」），描述「一个用户通常包含哪些字段」。
- **实例**：用户在设置里**新建 / 删除 / 编辑**的「具体的人」。
- 自动生成 ID：`user0`、`user1`、`user2` …（从 0 开始递增，方便后续被 App 引用，例如「现在发言的是哪个 user」）。

### 1.2 一个用户实例的字段

> 字段标记见 §0.2。符号：`R` = required（必填）、`O` = optional（可选）、`A` = advanced（仅详细模式）。

| 字段 | 模式 | 说明 |
|---|---|---|
| `id` | — | `user0`、`user1` … 自动生成（系统分配，不算填写字段）|
| `name` | 🔴 `R` | 显示名（如「我」「小张」） |
| `pronouns` | 🟡 `O` | 代词 |
| `summary` | 🟡 `O` | 一段话描述自己 |
| `preferences` | 🟡 `O` | 偏好（数组） |
| `notes` | 🟣 `A` | 备注（详细模式可见） |
| `tagRefs` | 🟡 `O` | **★ 标签引用**（见 §3.2），例如 `['tag-善良', 'tag-绒城居民']` |
| `currentLocationRef` | 🟣 `A` | `loc-xxx` \| null，**用户当前在哪个虚构地点**（不同于 AI 的当日快照） |
| `assets` | 🟣 `A` | **资产**（见 1.3） |
| `socialAccounts` | 🟣 `A` | **社媒账号**（见 1.4） |
| `createdAt` / `updatedAt` | — | 时间戳（系统自动） |

### 1.3 资产

- 资产定义在「用户实例」下，**不**单建库。
- 资产类型可枚举：现金 / 银行卡 / 虚拟币 / 游戏物品 / 自定义 …
- 每条资产：`{ type, label, amount?, currency?, meta? }`
- 后续 App（如记账 App、购物 App）**只读**用户的资产，按权限过滤后展示。

### 1.4 社媒账号（关键扩展点）

- 一个用户实例下挂多个社媒账号。
- 每条社媒账号：

```text
{
  id: 'sa-xxx',
  platform: 'weibo' | 'x' | 'wechat' | 'instagram' | 'bilibili' | 'custom',
  handle: '@xxx',
  displayName: '...',
  avatar: '...',
  credentials: { ... },        // 由对应 App 提供方写入，settings 不解析
  personaRef: 'ai0' | null,   // 这个账号由哪个 AI 人设来运营
  feedConfig: { ... },        // 这个账号能被哪些 App / 哪些 AI 读到
}
```

- **这里必须留 API**：其它 App（微博 App、朋友圈 App、X App）通过统一接口 `settings-sdk.socialAccounts.*` 注册和读取自己的账号信息。
- 后续做「AI 朋友圈」时，AI 人设读取该用户下挂的社媒账号，**按 platform 分别去对接对应 App** 的数据。
- **§3.16 自动派生**：当一个 AI 实例绑定了某个用户 + 某个世界观时，**自动派生**出该 AI 在该世界观下对应的社媒账号模板（仍要走用户手动"激活"才真正生成）。

### 1.5 用户库（集合）

- `users` 表：所有用户实例的列表。
- 设置主页新增「用户库」入口：列表 + 新建 + 删除 + 编辑 + 切换「当前用户」。
- **当前用户**概念：一个全局开关，告诉其它 App「现在操作的是哪个用户」。可以默认第一个，也可以在启动时让用户选。

## 2. AI 人设

### 2.1 AI 也是「原型 + 实例」

- 升级后**不**再是单条 `ai.name / ai.role / ai.tone / ai.rules`。
- 一个 AI 实例：

```text
{
  id: 'ai0',
  name: '默认 AI',                       // ★ required
  role: '通用助手',                       // ★ optional
  tone: '温柔克制',                       // ★ optional
  summary: '...',                        // ★ optional
  rules: [ ... ],                         // ★ optional
  notes: '...',                           // ★ advanced
  scope: 'global' | 'world:<worldId>',   // ★ optional  在所有世界观下生效 / 只在某个世界观下生效
  boundUserRef: 'user0' | null,          // ★ required  这个 AI 主要服务于哪个用户
  boundLocationRefs: ['loc-xxx', ...],   // ★ advanced  常驻哪些城市 / 阵营（决定能收到哪些天气）
  tagRefs: ['tag-善良', 'tag-侠客'],    // ★ optional  AI 身上的标签（见 §3.2）
  feedPermissions: { ... },              // ★ advanced  详见 §5
  // ----- 社交视角（见 §2.4）-----
  sentimentMap:  [...],                  // ★ optional
  relationMap:   [...],                  // ★ advanced
  // ----- 当日状态概率（见 §3.14）-----
  locationDistribution: [...],           // ★ advanced
  moodDistribution:     [...],           // ★ advanced
  locationOverride: null,                // ★ advanced  用户手动强制，覆盖当日快照（谨慎使用）
  moodOverride:     null,                // ★ advanced
  createdAt / updatedAt                  // 系统自动
}
```

**字段模式表**（标记来源见 §0.2）：

| 字段 | 模式 | 简略模式下写入规则 |
|---|---|---|
| `id` | 系统 | 自动 |
| `name` | 🔴 `R` | 必填 |
| `boundUserRef` | 🔴 `R` | 必填（明确"主服务用户"） |
| `role` | 🟡 `O` | 可空 |
| `tone` | 🟡 `O` | 可空 |
| `summary` | 🟡 `O` | 可空 |
| `rules` | 🟡 `O` | 可空（数组） |
| `scope` | 🟡 `O` | 默认 `'global'` |
| `tagRefs` | 🟡 `O` | 可空 |
| `sentimentMap` | 🟡 `O` | 可空 |
| `notes` | 🟣 `A` | 仅详细模式可见 |
| `boundLocationRefs` | 🟣 `A` | 仅详细模式可见 |
| `feedPermissions` | 🟣 `A` | 仅详细模式可见 |
| `relationMap` | 🟣 `A` | 仅详细模式可见 |
| `locationDistribution` / `moodDistribution` | 🟣 `A` | 仅详细模式可见 |
| `locationOverride` / `moodOverride` | 🟣 `A` | 仅详细模式可见 |

### 2.2 多 AI

- 用户可以建多个 AI 实例，每个 AI 有自己的名字 / 语气 / 规则。
- 不同 App 可以绑定不同 AI，例如：
  - 「微博 App」绑 AI「娱乐博主小助手」
  - 「学习 App」绑 AI「严谨导师」
  - 「陪伴 App」绑 AI「温柔朋友」
- **当前 AI** 概念：默认 AI（被所有未绑定的 App 使用）。

### 2.3 跟用户一样有「库」

- `aiPersons` 表：所有 AI 实例。
- 设置主页新增「AI 库」入口。

### 2.4 ★ AI 的「社交视角」—— sentimentMap / relationMap（替代原圈子模型）

> 原圈子 (Circle) 的 relations 字段**已废弃**。
> 新模型：**每个 AI 各自维护一份"我对他人怎么看"**——同一对关系在不同 AI 眼里可以是敌是友。

#### 2.4.1 两种关系并存

| 字段 | 含义 | 适合 |
|---|---|---|
| `sentimentMap` | **情感类**关系（朋友 / 敌人 / 师徒 / 暗恋） | 程序化判定 + AI 行为参考 |
| `relationMap` | **自定义字符串**关系（"义兄"/"宿敌"/"前女友的妹妹"） | AI 自由发挥，更像人话 |

```text
sentimentMap: [
  { targetRef: 'user0', sentiment: 'friend',    note: '一起长大的邻居', inferred: false, createdAt: ... },
  { targetRef: 'ai1',   sentiment: 'rival',     note: '读书时一直压我一头', inferred: true,  createdAt: ... },
  { targetRef: 'ai2',   sentiment: 'swornEnemy',note: '杀父之仇',           inferred: false, createdAt: ... },
  { targetRef: 'ai3',   sentiment: 'mentor',    note: '我的剑术启蒙师父',   inferred: true,  createdAt: ... },
],
relationMap: [
  { targetRef: 'user0', relation: '义兄', note: '小时候结拜的', inferred: false },
  { targetRef: 'ai2',   relation: '宿敌', note: '三十年前的剑崖决斗', inferred: false },
],
```

#### 2.4.2 `inferred` 字段 —— 谁写的

- `false`：**用户手写**的基础关系（在设置里填的）。
- `true`：**AI 对话过程中产生的**（AI 说"我跟 ai2 是宿敌"），落到库里后给用户一个"是否接受"的提示（动态岛），用户可「接受 / 拒绝 / 编辑」。

#### 2.4.3 调用接口

```text
// 注入 AI 上下文时
settings-sdk.social.getRelations('ai0', 'user1')
// → [
//   { sourceRef: 'ai0', targetRef: 'user1', sentiment: 'friend', note: '...' },
//   { sourceRef: 'ai0', targetRef: 'user1', relation:  '义兄',  note: '...' },
// ]
```

#### 2.4.4 为什么**不**存在 tag 系统里？

- tag 是**多对多对称**的（user0 有 [善良, 学生]，ai0 也可能有 [善良]）。
- sentiment/relation 是**有向非对称**的（ai0 认为 ai1 是朋友，ai1 可以认为 ai0 是敌人）。
- 混在一起会让数据变复杂。**情感/关系单独存**，标签存身份属性。

## 3. 世界观（最重的一块）

### 3.1 世界观 = 合集 + 实例

- 现状只有「一个世界观」，要升级为「**世界观库** + **当前世界观**」。
- 一个世界观实例：

```text
{
  id: 'world0',
  name: '绒城纪事',              // ★ required
  summary: '一句话主旨',           // ★ required
  keyPoints: [ ... ],            // ★ optional
  timeline: [ ... ],             // ★ optional
  notes: '...',                  // ★ advanced
  tagRefs: ['tag-古风', 'tag-低魔'],   // ★ optional  世界观本身的标签
  factions: [ ... ],             // ★ advanced  阵营列表（字段名保留，UI 名称见 §3.9）
  locations: [ ... ],            // ★ optional  城市 / 地点列表（见 3.3）
  calendarSettings: { ... },     // ★ advanced  日历设置（见 §3.6）
  holidays: [ ... ],             // ★ advanced  节日（见 §3.7）
  eventAggregator: { ... },      // ★ advanced  个人事件聚合开关（见 §3.8）
  createdAt / updatedAt
}
```

**字段模式表**（标记来源见 §0.2）：

| 字段 | 模式 | 简略模式下写入规则 |
|---|---|---|
| `id` | 系统 | 自动 |
| `name` | 🔴 `R` | 必填 |
| `summary` | 🔴 `R` | 必填（一句话主旨） |
| `keyPoints` | 🟡 `O` | 可空 |
| `timeline` | 🟡 `O` | 可空 |
| `tagRefs` | 🟡 `O` | 可空 |
| `locations` | 🟡 `O` | 可空（简化场景下"零地点"也合法） |
| `notes` | 🟣 `A` | 仅详细模式可见 |
| `factions` | 🟣 `A` | 仅详细模式可见 |
| `calendarSettings` | 🟣 `A` | 仅详细模式可见 |
| `holidays` | 🟣 `A` | 仅详细模式可见 |
| `eventAggregator` | 🟣 `A` | 仅详细模式可见 |

> **注意**：World 实例**不存任何业务数据**（商品 / 任务 / 成就 等都不在这里）。它是"世界的壳"，具体内容由各 App 自己去读 world → 调 AI → 自己的表里存。详见 §3.4。

> **★ 维度类需求一律走"标签组"**（v0.4 新约定）：如果未来想加"权力结构 / 经济体系 / 禁忌"这类维度，**不要**在这里加字段——而是让用户在标签组里自己建（"京城名流""社会结构""商帮"…）。详见 §3.2。

- **当前世界观**：全局开关，决定 AI 默认在哪个世界观下回答。
- **注意**：简略模式下用户**仍能完整使用**世界观——`name` + `summary` + `locations` 已经够 AI 在里面聊了；其余字段是真要用到时再切到详细填。

### 3.2 ★ 标签 + 标签组（Tag + Tag Group）—— 替换原「圈子 (Circle)」

> **删除**了原圈子 (Circle) 整章（v0.2 之前叫"§3.2 圈子"，现 §3.2 改为标签系统）。
> 原因：你说"社交圈到时候在 ai 那部分设置好了"——也就是关系性数据是 **AI 主观的**，不属于某个静态合集。
> 标签只承担**身份 / 属性 / 分桶**作用。

#### 3.2.0 ★ 为什么需要"标签组"

> 用户的核心场景（v0.4 提出）：「我不想在世界观字段里硬塞『权力结构 / 经济体系』这种东西。我想让用户自己建一个标签组叫『京城名流』，里面放 F5 / 小时代 / 老钱新贵……」

**结论**：标签本身只是"点"。**"维度"由标签组承担**。
- 标签 = 维度上的一个**取值**（比如 `F5`、`老钱新贵`）
- 标签组 = 一个**维度**本身（"京城名流"这个分类法）

没有组的话，用户要建 100 个标签才能描述 5 个维度；有了组，每个维度就是一个收纳盒。

#### 3.2.1 标签组（Tag Group）的定义

```text
// tagGroups 表里的每条记录
{
  id: 'tgroup-xxx',
  scope: 'global' | 'world:<worldId>',   // ★ global 可跨世界复用；world:<id> 仅该世界
  name: '京城名流',                       // UI 显示名
  displayName: '京城名流',
  description: '绒城里活跃的社交圈层',     // 可选说明
  color: '#fbbf24',                       // 整个组的主色（组下标签可继承）
  icon: '<svg>...</svg>',                 // 可选
  // 排序 / 系统性约束
  isSystem: false,                        // 系统预设的（如「性格」「阵营」）用户不能删
  // 私密性
  visibility: {
    default: 'private',
    allowedAiRefs: [],
    allowedUserRefs: [],
  },
  createdAt / updatedAt
}
```

#### 3.2.2 标签（Tag）的定义 —— 现在挂在组下面

```text
// tags 表里的每条记录
{
  id: 'tag-xxx',
  groupId: 'tgroup-京城名流',             // ★ 必填：所属组（v0.4 强制要求）
  scope: 'global' | 'world:<worldId>',   // ★ 跟 group 保持一致（不必独立设置）
  name: 'F5',
  displayName: 'F5',
  aliases: ['京圈 F5', '京城五少'],       // 搜索 / 模糊匹配候选
  color: '#ec4899',                       // 可选；不填则继承组 color
  icon: '<svg>...</svg>',
  notes: '绒城最顶级的名流圈层，五大家族子弟',
  visibility: {
    default: 'private',
    allowedAiRefs: [],
    allowedUserRefs: [],
  },
  createdAt / updatedAt
}
```

**关键变化（v0.4）**：
- 标签**必须有 `groupId`**——不再允许"散装标签"。
- 一个组下面的标签天然**互斥或并列**（取决于组定义），用户用一组就锁了一个维度的选择。

#### 3.2.3 系统预设组（第一版就内置）

第一版**就**内置 6 个常用组，让用户拿来即用：

| 组 id（建议） | 名称 | 用途 | 推荐标签 |
|---|---|---|---|
| `tgroup-personality` | 性格 | 描述对象的核心性格 | 善良、温柔、阴沉、神经质、社恐、外向 |
| `tgroup-faction` | 阵营 | 对象归属 / 立场 | 正义、中立、邪恶、皇权派、革命党 |
| `tgroup-occupation` | 职业 | 对象的社会身份 | 学生、商人、侠客、医生、AI |
| `tgroup-species` | 种族 / 物种 | 对象是什么"人" | 人类、妖族、改造人、神族 |
| `tgroup-mood` | 心情 / 状态 | 当下情绪（可被 sentimentMap 引用） | 平静、烦躁、心动、绝望 |
| `tgroup-genre` | 风格 / 调性 | 世界观的艺术风格 | 古风、赛博朋克、像素、低魔、治愈 |

> 这些**预设组**打 `isSystem: true`——用户可以加标签但不能改组名 / 不能删组。
> 用户**可以**自己建任意自定义组（如「京城名流」「设计圈」）。

#### 3.2.4 标签怎么挂到对象上

对象身上有一个字段 `tagRefs: ['tag-F5', 'tag-善良']`。**对象身上的标签随对象走**——但**推荐约定**：

- **"性格 / 种族 / 职业"组**下的标签 → 对象**自己**带着（跨世界观不变）✅
- **"阵营 / 京城名流 / 设计圈"组**下的标签 → **强烈建议**只挂在指定世界观下的对象上

#### 3.2.5 标签的查询 API

```text
// 找组（UI 上"选择标签"的下拉就是按组分组的）
settings-sdk.tagGroups.getAll({ scope: 'world:<worldId>' | 'global' })
settings-sdk.tagGroups.getById('tgroup-京城名流')

// 找标签（按组筛）
settings-sdk.tags.findByGroup('tgroup-京城名流')                  // 该组所有标签
settings-sdk.tags.findByGroup('tgroup-京城名流', { worldId: 'world0' })  // 仅 world0

// 按标签找对象（跟 v0.3 一致）
settings-sdk.tags.findObjectsByTag('tag-F5')
settings-sdk.tags.findObjectsByTags(['tag-F5', 'tag-老钱新贵'], 'OR')

// ★ 新增：按组查所有"贴了这个组的标签"的对象
settings-sdk.tags.findObjectsByGroup('tgroup-京城名流', 'OR')
// → ['ai-小王爷', 'ai-商贾千金', ...]
```

#### 3.2.6 ★ 用法示例 —— 你刚才提的那个

```
用户给"绒城纪事"建了一个标签组「京城名流」
  └─ F5
  └─ 小时代
  └─ 老钱新贵

用户给 AI「小王爷」贴上 tag-F5

回到绒城纪事 → 在「京城名流」组下 → 看到「小王爷」 ✅
切到修仙世界 → 在「京城名流」组下 → 看不到「小王爷」（因为他没贴这个世界观的标签）✅
```

> **这就是你想要的"AI 在这个世界观里被某个标签收编"的体验**。
> 实现就一行：`settings-sdk.tags.findObjectsByGroup('tgroup-京城名流', 'OR')`。

#### 3.2.7 跟节日 / ACL 的搭配

§3.7 节日的 `visibleTo.circles` 字段**改为** `visibleTo.tagRefs`：

```text
holiday = {
  ...
  visibleTo: {
    tagRefs: ['tag-善良', 'tag-朋友'],   // ★ 替换 circles
    userRefs: ['user0'],                 // 也可显式列人（向后兼容）
    aiRefs:   ['ai0', 'ai1'],            // 也可显式列 AI
  },
}
```

读节日时按 §3.2.7 的"集合交并"逻辑：对象身上的 `tagRefs` 跟节日的 `visibleTo.tagRefs` 有交集 → 可见。

### 3.3 城市 / 地点（Location）

- 地点也属于「某个世界观实例」下。
- 一个城市：

```text
{
  id: 'loc-xxx',
  worldRef: 'world0',
  name: '绒城',
  realCityRef: 'hangzhou' | null,  // ★ 关键：映射到真实城市
  factionRef: 'fac-xxx' | null,    // 归属阵营
  occupants: ['user-x', 'ai-y'],   // 哪些用户 / AI 常驻此地
  tagRefs: ['tag-繁华', 'tag-港口'],// ★ 城市自身的标签
  summary: '...',
}
```

- `realCityRef` 是**天气 App 的接口约定**：天气 App 读取当前世界观的 `locations[*].realCityRef`，把真实城市的天气**映射**回这个虚构城市的天气。
- 例如：把杭州天气映射成绒城天气 → 天气 App 显示「绒城 · 多云转晴 · 27°C」，后续聊天 App 的 AI 也能读取「今天绒城天气：晴」。

### 3.4 商品数据归属：World 是**只读信息源**，具体商品由各 App 运行时生成

> **核心立场**：世界观实例**不存**任何具体商品数据。它只存"这个世界观是什么"（summary / keyPoints / locations / tagRefs）。
> 谁要卖货，谁（App 自己）去读 world 实例 + 调 AI + 自己生成商品并自己存。

#### 3.4.1 数据流

```
世界观的"卖点摘要"（用户在 world.summary / world.keyPoints 里写的）
        │
        ▼
购物 App 启动 / 用户进入商品列表
        │
        ▼
购物 App 调 settings-sdk.world.getActive()
   → 拿到 { id, name, summary, keyPoints, tagRefs, locations, ... }
        │
        ▼
购物 App 把这段"世界观信息"作为 prompt 上下文喂给 AI
        │
        ▼
AI 实时生成 5-20 件商品（名称 / 分类 / 价格 / 描述 / 图）
        │
        ▼
购物 App 自己存到自家表 products 里（持久化 + 缓存）
下次再打开同一个世界观 → 缓存命中 → 不重算
```

#### 3.4.2 World 字段表里没有 `productSeeds` / `products` / 任何商品字段

世界观实例**保持纯粹**——只描述"这是个什么世界"，不预设任何具体业务数据。
其它 App（购物 / 任务 / 成就 / 剧情 …）都按上面 3.4.1 那条流走：**读 world → 调 AI → 自己的表存**。

#### 3.4.3 为什么不做预置种子

- 世界观的"能卖什么"是**无限延展的**，预先枚举 = 限制 AI 的创造力。
- 不同世界观（古风 / 赛博 / 修仙）下"商品"边界完全不同，预置模板很难通用。
- **World 实例只要够"细"（summary + keyPoints 写得详细）**，AI 自然能生成符合这个世界观的商品；world 写得粗也没关系——生成得粗一些用户也接受。
- 用户体验上：每次切世界观都能看到"AI 按这个世界观新生成的一批商品"是**正反馈**，不是负担。

#### 3.4.4 与 §5.3 注入管道的关系

购物 App 在 §5.3 第 ② 步（**世界背景**）里**自动**拿到完整的世界观信息——这部分是免费的，不用购物 App 自己写读 world 的代码。购物 App 只需要在生成商品前确认已经走完 `feed.collectForAi` 的 ①② 步，③-⑦ 步用不上。

#### 3.4.5 缓存策略建议（购物 App 自己定）

| 维度 | 建议 |
|---|---|
| 何时重算 | 用户切换到其它世界再切回来 → 重新生成（避免"古风世界里的商品一直停在第一次进入的样子"） |
| 用户手动刷新 | 提供"换一批"按钮 → 重新调 AI 生成 |
| 缓存粒度 | 按 `world.id` 缓存，不是按 `user.id` |
| AI 上下文裁剪 | 喂 AI 时只传 world 关键字段（id / name / summary / keyPoints / tagRefs），不要把整个 world 实例全塞进去 |

### 3.5 时间线 / 编年史

- 现状是字符串，建议升级为结构化：

```text
{ year: 1024, label: '绒城建城', description: '...' }
```

- 同时支持**日历 / 时间表 App** 读取，做「世界内事件」视图。

### 3.6 日历设置（世界观级）

> 有些世界观一周七天 + 工作日，有些世界观可能根本没有"工作日"的概念（比如修仙世界"闭关"）。这是**世界观实例的属性**，不是个人属性。

```text
{
  hasWorkday: true | false,           // 这个世界观是否有"工作日 / 休息日"概念
  weekDays: ['月曜', '火曜', ...],    // 自定义一周的名字（西幻可用"工匠日 / 法师日"）
  workdays: [1,2,3,4,5],              // 哪些是工作日（按 weekDays 序号）
  calendarSystem: 'gregorian' | 'fantasy' | 'custom',
  yearLabel: '帝国历',                // 纪年标签
}
```

- **直接影响 AI 的语义**：绒城世界观里 AI 知道"明天是工匠日休市"，现代世界观里 AI 知道"明天是周六不用上班"。

### 3.7 节日（Holidays）

> 节日属于**世界观**，所有被授权的人共享；个人事件属于**个人日历**，只对自己和被授权的 AI 可见。

```text
{
  id: 'hol-xxx',
  worldRef: 'world0',
  name: '绒城灯节',
  date: { month: 2, day: 7 },         // ★ 简化：按"月-日"重复，跨年有效
  recurrence: 'yearly',               // 'yearly' | 'oneOff' | 'weekly' | 'custom'
  summary: '绒城一年一度的灯火节，家家户户放河灯',
  customs: ['放河灯', '吃元宵'],     // 习俗，AI 可以聊到
  visibleTo: {                        // ★ ACL：哪些对象在这个节日里能看到
    tagRefs:  ['tag-善良', 'tag-朋友'],  // 持有任一标签的对象可见
    userRefs: ['user0'],
    aiRefs:   ['ai0', 'ai1'],
  },
  feedEnabled: true,                  // ★ 节日当天，是否让 AI 在聊天里自动提
}
```

- **读取逻辑**（settings-sdk 在聊天 App 调用时执行）：
  1. 算出"今天在当前世界观下是不是节日"。
  2. 取出 `visibleTo` 命中的对象列表（tagRefs 命中 OR userRefs 命中 OR aiRefs 命中）。
  3. 当前对话的对象在名单里 → 把节日摘要 / 习俗注入到 AI 上下文。
  4. 不在名单里 → 不注入。

### 3.8 个人事件投射到世界观（最巧的一招）

> 「个人大事 / 课程表绑定到世界观后，自动同步到世界观的日历视图里」—— 这里的关键设计是：**个人事件不复制到世界观，只是被引用**。

#### 双层结构

- **个人层（Calendar App 的 owner = user / ai）**——数据真身在「日历 App」表里。
- **世界观层（聚合视图）**——世界观实例上**不存具体事件**，只存一个**事件聚合开关**：

```text
{
  includePersonalEvents: true | false,           // 世界观日历是否展示个人事件
  includedOwners: ['user0', 'user1', 'ai0'],     // 哪些 user / ai 的事件投到这个世界观
  visibility: {
    toUserSelf: true,                            // 个人看自己：永远能看
    toOtherUsers: false,                         // 别的用户看你的事件：默认不可见
    toAiPersons: ['ai0'],                        // 哪些 AI 能读到这些个人事件
  },
  showInWorldTimeline: true,                     // 在世界时间线上是否显示
  displayStyle: 'dot' | 'badge' | 'inline',      // 视觉上怎么混进世界事件
}
```

#### 读取流程

1. 聊天 App 准备给 AI0 喂上下文。
2. settings-sdk 看到当前世界 = `world0`。
3. `world0.includePersonalEvents === true` 且 `includedOwners` 包含 owner → 把这些 owner 在「日历 App」里的事件**按 visibility 过滤**后注入。
4. 注入时**自动标注来源**：「[user0 个人] 周三下午有数据结构课」—— 跟世界观事件「[世界] 周五是绒城集市日」**视觉上区分**。

> 这就是「**Reference（引用）**」的实战：**数据只存一份，靠引用聚合视图，避免数据不一致。**

#### 典型场景

- 小张绑在「绒城」+「工作日表」上 → 周三下午的"数据结构课"自动出现在绒城的日历上。
- 小张的生日 → 在绒城日历上变成「[user0 生日] 绒城居民小张生日」。
- 修仙世界不绑工作日，只绑个人事件 → 世界观日历只显示"闭关日"等个人事件，工作日概念不存在。

### 3.9 阵营（Factions）—— 保留字段名但语义变化

> 注意：**删的是"圈子 (Circle)"，阵营字段保留**，但阵营现在只是个**轻量分桶**——它可以自动跟"标签"双向同步。

- 阵营属于「某个世界观实例」下，跟原来一样。
- **变化**：阵营成员 (`memberRefs`) 跟标签系统**互相投影**：
  - `fac-xxx.memberRefs` ↔ 这些 user/ai 身上的 `tagRefs: ['tag-阵营-守夜人']` 自动双向同步
  - 即"加入阵营"= 自动给自己加一个 `tag-阵营-<名>` 的标签
- **关系判定不再走阵营.relations**——改走 §2.4 AI 的 sentimentMap / relationMap。

```text
{
  id: 'fac-xxx',
  worldRef: 'world0',
  name: '绒城守夜人',
  displayName: '守夜人',
  summary: '...',
  memberRefs: ['user0', 'ai0'],     // ★ 加入/离开会自动同步标签
  derivedTagId: 'tag-阵营-守夜人',   // 自动派生的标签 id
  color / icon: '...',
}
```

### 3.14 ★ AI 当日状态：位置概率 + 心情概率

> 本节是 §3.15 快照表的**输入**。

#### 3.14.1 字段定义（在 ai 实例上）

```text
locationDistribution: [
  { locationRef: 'loc-绒城',   weight: 90 },   // 90% 概率在绒城
  { locationRef: 'loc-A城',    weight: 10 },   // 10% 概率在 A 城
],
moodDistribution: [
  { mood: 'happy',      weight: 50 },          // 第一版：离散 mood 字符串
  { mood: 'calm',       weight: 30 },
  { mood: 'melancholy', weight: 20 },
],
locationOverride: null,        // ★ 用户手动强制（覆盖今日快照，谨慎使用）
moodOverride:     null,
```

#### 3.14.2 心情的两种表达（**我替你定的，不同意告诉我**）

第一版只用**离散字符串**（happy / calm / melancholy / excited / lonely / angry...），UI 上友好、AI 也好理解。
后续如果需要更细的"情绪维度"，再加 `valence` / `arousal` / `dominance` 三个 0-1 浮点数（参考心理学 PAD 模型）。**当前不做**。

#### 3.14.3 加权随机算法

```js
function weightedPick(distribution, rng = Math.random) {
  const total = distribution.reduce((s, d) => s + d.weight, 0);
  let r = rng() * total;
  for (const d of distribution) {
    r -= d.weight;
    if (r <= 0) return d;
  }
  return distribution[distribution.length - 1];   // 浮点兜底
}
```

#### 3.14.4 跟 locationOverride 的关系

| 字段 | 行为 |
|---|---|
| `locationOverride = 'loc-绒城'` | 当日快照**直接强制**为绒城，跳过概率分布 |
| `locationOverride = null` | 走 §3.15 快照逻辑（首次算，缓一整天） |

### 3.15 ★ 当日快照（Daily Snapshot）—— 概率落地的关键表

> **核心问题**：AI 的"今天在绒城 / 今天心情好"是**概率算出来的**，但**每次对话不应该重新算**——今天的 AI 跟早上的 AI 是同一个状态的 AI。

#### 3.15.1 数据模型

```text
// 新表 dailySnapshots，keyPath = 'key'
{
  key:    'ai0|2026-07-14',     // ★ 主键 = aiId + 本机本地日期
  aiId:   'ai0',
  date:   '2026-07-14',
  location: { ref: 'loc-绒城', label: '绒城' },    // ★ 算出来的当日位置
  mood:     'happy',                                // ★ 算出来的当日心情
  // ---- 留扩展位（先做占位，不读不写）----
  weather:      null,   // §3.3 realCityRef + 天气 App 后期填
  holidayHits:  [],     // §3.7 节日命中列表
  derivedAt:    1720900000000,   // 时间戳（毫秒）
  source:       'computed',      // 'computed' | 'override' | 'manual'
}
```

#### 3.15.2 核心 API：`getOrCompute` —— 选项 1 缓存语义

```text
settings-sdk.snapshot.getOrCompute('ai0', {
  onCompute: () => ({
    location: weightedPick(ai0.locationDistribution),
    mood:     weightedPick(ai0.moodDistribution),
  })
})
// → 如果今天算过了 → 直接返回缓存的快照
// → 如果今天没算过 → 调 onCompute 算一次，写库，返回新快照
```

**缓存语义（选项 1，已拍板）**：

> 今天第一次跟 ai0 聊天 → 算概率（比如命中绒城）→ 写快照 `ai0|2026-07-14 = 绒城`
> 今天第二次跟 ai0 聊天 → 直接读缓存，不算
> 今天第三次跟 ai0 聊天 → 直接读缓存，不算
> 今天我把 ai0.locationDistribution 改成 100% A 城 → **今天**ai0 还是在绒城（缓存优先）
> 明天跟 ai0 聊天 → 算新的，命中 A 城 → 写 `ai0|2026-07-15 = A 城`

**为什么选 1**：
- 符合"缓存"语义；
- 调试可重现（看到 `ai0|2026-07-14 = 绒城` 就知道今天 AI 一整天都是绒城）；
- UI 可以做"今日 AI 状态卡片"明示：「今天小张在绒城 · 心情 happy · 下次算概率时是新的」；
- 防止用户改概率分布后看到 AI 在两次回复之间"瞬间位移"的诡异感。

#### 3.15.3 辅助 API

```text
// 强制重算（调试 / 用户改概率 + 显式按"立即重算"按钮时）
settings-sdk.snapshot.recompute('ai0')

// 查某 AI 的历史快照（调试面板：日历视图，看 AI 历史上哪天在哪里）
settings-sdk.snapshot.listForAi('ai0', { from: '2026-07-01', to: '2026-07-31' })

// 查今天的快照（只读，不算）
settings-sdk.snapshot.getToday('ai0')

// GC：清理 N 天前的快照（避免无限累积）
settings-sdk.snapshot.gc({ keepDays: 90 })
```

#### 3.15.4 触发位置

- **不在框架层强制**——`getOrCompute` 是 App 主动调用的工具方法。
- **典型调用点**：
  - 聊天 App 准备发消息给 AI 前 → 调一次
  - 微博 App 准备用 AI 生成内容前 → 调一次
  - 学习 App 调 AI 讲解题前 → 调一次
  - **同一天同一 AI 跨 App 多次调用** → 全部命中同一条快照

#### 3.15.5 缓存键的边界条件（**我替你定的，不同意告诉我**）

| 维度 | 处理 |
|---|---|
| 时区 | 用本机本地日期（`new Date().toLocaleDateString('en-CA')` → 'YYYY-MM-DD'）。**不处理跨时区**，单机 App 没必要 |
| 时钟漂移 | 跟系统时钟走。午夜 0 点跨日 → 新一天的 key 不存在 → 重新算 |
| 用户改 AI 名 / 改 distribution | **不影响**今天快照（缓存语义选项 1） |
| 用户设了 locationOverride | 直接写 `source: 'override'` 的快照，跳过概率 |
| 用户删了 AI | 对应快照 gc 时清理 |

### 3.16 ★ 社交账号自动派生（社媒账号从 AI 自动生成）

> 当一个 AI 绑定了用户 + 世界观后，**自动生成**该 AI 在该世界观下"应当拥有"的社媒账号模板，用户可一键激活。

#### 3.16.1 派生规则

```text
// 触发：创建/编辑 AI 时，AI 满足以下条件：
if (ai.boundUserRef && ai.scope.startsWith('world:')) {
  // → 为该 AI 在该 user 下生成"账号骨架"
  // → 但不写入 socialAccounts（要用户手动激活）
  // → 放到 aiAccountsTemplate（一个新表 / 或 ai 实例上的 pendingSocialAccounts）
}
```

#### 3.16.2 派生字段

```text
{

  forAiRef:  'ai0',
  forUserRef:'user0',
  inWorldRef:'world0',
  platform:  'weibo',                  // 根据 AI.role / AI.tone 自动建议

  suggestedDisplayName: '绒城小张',
```

#### 3.16.3 激活流程

## 4. 时间表 + Todo（用户 & AI 都有）

### 4.1 双层结构

- **个人层**：日历 App / Todo App 是**唯一数据源**，owner 字段区分人。

```text
calendarEvent = {
  id: 'ev-xxx',
  ownerType: 'user' | 'ai',          // 谁的事件
  ownerRef: 'user0' | 'ai0',
  title: '数据结构课',
  start: '2026-09-01T14:00',
  end:   '2026-09-01T15:30',
  recurrence: 'weekly' | 'oneOff' | 'yearly',
  category: 'class' | 'work' | 'life' | 'birthday' | 'anniversary',
  visibility: 'self' | 'public' | 'custom',
  ...
}
```

- **聚合层**：见 §3.8，个人事件通过**引用**投射到世界观日历。

### 4.2 抽成独立 App：「日历」

- 日历 App 同时服务于「用户日程」和「AI 日程」两种 owner。
- 其它 App 写入日程时走日历 App 的统一接口（或 `settings-sdk.calendar.add(...)`）。

### 4.3 Todo

- 同样抽成独立 App「Todo」，owner = user 或 ai。
- 「智能选择是否开启」：每个 AI 实例下挂 `todoConfig.autoInject: boolean` —— 开启后，AI 在每次回复前自动注入今天的 todo 作为上下文。
- **Todo 也走 §3.8 那套** —— Todo 完成的"高优任务"可以选择性投射到世界观的"今日待办"视图。

### 4.4 个人时间表 vs 工作日冲突处理

> 你提的「现代世界观有工作日 / 修仙世界观没有」—— 这是**两个层级**的问题：

| 层 | 谁负责 | 例子 |
|---|---|---|
| **世界观日历设置**（§3.6）| 世界观实例自己有没有"工作日"概念 | 修仙世界观：`hasWorkday: false` |
| **个人日程**（§4.1）| 个人真的去不去上班 / 上不上课 | user0 的"周三数据结构课" |
| **聚合**（§3.8）| settings-sdk 把两者拼起来 | 修仙世界观里 user0 的"周三闭关"才会显示，"上班"根本不出现 |

> 关键：**不要让个人日程去适配世界观**，而是**世界观只决定"显示哪些 / 不显示哪些 / 怎么命名"**。这样切换世界观时，个人日程数据原封不动，只是换个滤镜。

## 5. App 数据源 + 权限矩阵 + 上下文组装器

> 本章拆成三段：**注册 → 授权 → 组装**。这是 §0.1 管道图的 ⑥⑦ 步。

### 5.1 注册：所有 App 声明自己提供哪些数据

每个 App 启动时**向 settings-sdk 注册自己能贡献的数据源**：

```text
settings-sdk.dataSources.register({
  appId: 'weibo',
  sourceId: 'weibo.feed',
  label: '微博动态',
  description: '我发布过的微博',
  schema: { ... },                // 可选，描述字段
})
```

settings 里看到的是一组「数据源清单」。

### 5.2 授权：每个 AI 各自的权限矩阵

每个 AI 实例下挂 `feedPermissions`：

```text
feedPermissions: {
  // —— 静态过滤 ——
  include: ['weibo.feed', 'wechat.dm'],         // 白名单（与 byApp 二选一或并存）
  exclude: ['gallery.private'],                  // 黑名单，优先级最高
  
  // —— 按 App 开关（更直观，第一版主推）——
  byApp: {
    'weibo':   { enabled: true,  scope: 'public' | 'all' },
    'wechat':  { enabled: true,  scope: 'dm-only' | 'all' },
    'gallery': { enabled: false },
  },
  
  // —— 时间窗口（节日 / 个人事件专用）——
  timeWindows: {
    'hol-xxx': {              // 仅在节日 hol-xxx 当天生效
      enabled: true,
      window: 'onDay',        // 'onDay' | 'range' | 'always'
      range: { from: '...', to: '...' },
    },
    'calendar.user0': {       // 仅个人事件 owner = user0 时
      enabled: true,
      ownerScope: 'self',     // 'self' | 'public' | 'custom'
    },
  },
}
```

### 5.3 ★ 组装器：上下文注入管道（呼应 §0.1，受 §0.2 profile 过滤）

`settings-sdk.feed.collectForAi(aiId, options)` 是**整个 AI 上下文注入的统一入口**：

```text
const ctx = await settings-sdk.feed.collectForAi('ai0', {
  world: 'world0',             // 默认当前世界观
  user:  'user0',              // 默认当前用户
  app:   'wechat',             // 当前 AI 所在的 App（用于 byApp 过滤）
  mode:  'systemPrompt',       // 'systemPrompt' | 'chatHistory' | 'summary'
})
```

#### 组装顺序（严格按以下顺序）

1. **基础身份** — ai 实例的 name / role / tone / rules + user0.name + ai.tagRefs（已展开成"组名:标签名"的形式，例如 `「京城名流:F5」「性格:善良」`）。
   - **★ 按 §0.2 profile.level 过滤可见字段**：
     - `detailed` 模式 → 把 ai 全部非空字段 + 所有 sentimentMap / relationMap 注入
     - `minimal` 模式 → 只注入 ai.summary + name + tone + 基础 sentimentMap（`A` 字段 `relationMap`、`boundLocationRefs`、`locationDistribution`、`moodDistribution`、`feedPermissions` 等不进入 systemPrompt）
2. **世界背景** — world 实例的 summary / keyPoints / 当前 world 下的 locations/factions 列表。
   - 同样按 profile.level 过滤：minimal 模式只注入 summary + locations 名；detailed 模式注入 factions / keyPoints / timeline。
3. **★ 标签组全集**（v0.4 新增）— 当前世界观下所有 `scope='world:<worldId>'` 的标签组，以及它们下面的标签。
   - 注入形式：
     ```
     当前世界观「绒城纪事」下有以下标签组：
       - 「京城名流」：F5、小时代、老钱新贵
       - 「社会结构」：皇权至上、商贾崛起
       - 「设计圈」：鹅厂系、字节系
     这些标签都可以挂到 user / ai / location / faction 上。
     AI 在这个世界观里可以**主动**给对象贴标签，也可以基于用户描述推断。
     ```
   - **为什么必须注入全集**：用户会问"老钱新贵有谁"、"现在贴了 F5 标签的 AI 都是谁"——AI 必须知道有哪些可选项才能正确回答。
   - 标签组里的所有标签**对当前 AI 可见**（按 visibility.default + allowedAiRefs 过滤）。
4. **★ 当日快照** — `getOrCompute(ai0, ...)` 拿到今天的 location / mood / weather。
5. **社交视角** — ai.sentimentMap + relationMap（按 §2.4） + ai.tagRefs。
6. **日历 / 事件** —
   - world.holidays 按 `visibleTo.tagRefs/userRefs/aiRefs` 过滤 → 今日命中项
   - user/ai.calendarEvents 按 §3.8 投射规则过滤 → 今日命中项
7. **App 数据源** — 按 ai.feedPermissions 过滤所有注册过的 dataSources：
   - 先按 `byApp` 过滤当前 App 是否启用
   - 再按 `include/exclude`
   - 再按 `timeWindows`
   - 最后按 dataSource 自己的权限（有些 App 自带 "public/private" scope）
8. **拼模板** — 按 mode 拼成 systemPrompt / chatHistory 摘要 / 单条 summary 字符串。

#### 5.3.1 缓存层级

| 缓存对象 | 缓存位置 | 失效时机 |
|---|---|---|
| 当日快照 | IndexedDB `dailySnapshots` 表 | 见 §3.15 |
| feed.collectForAi 结果 | **第一版不缓存**，每次都重新拼（数据源实时性强） | — |
| ai 实例本身 | 内存 + IndexedDB | 用户编辑时 |
| world 实例本身 | 内存 + IndexedDB | 用户编辑时 |

## 8. 待你拍板的开放问题

1. **「当前用户 / 当前 AI / 当前世界观」是全局单选还是按 App 单独记忆？**
   建议：全局单选（最简单），后续如果需要按 App 切换，再加 `appScope` 字段。

2. **同一个 user 同时属于不同世界观的圈子怎么办？**
   已通过 §3.9 解决：阵营成员 ↔ 标签系统双向投影。**已不再算问题**。

3. **节日用公历还是农历 / 自定义？**（见 §3.7）
   建议：date 字段支持 `{ month, day }` / `{ lunarMonth, lunarDay }` / `{ customExpr }` 三种表达，第一版只做公历。

4. **★ 各 App 在不预存的情况下，"世界观的描述颗粒度"够不够生成合格商品？**（新增 / v0.4）
   之前版本计划"商品种子手动录入"，改为"读 world → AI 生成"。但 AI 生成质量取决于 world.summary / keyPoints / tagRefs 写得有多细。
   建议：第一版只要 `summary` 不为空 + `tagRefs` 至少一个标签就行；用户想"商品丰富"再去详细模式补 `keyPoints`。如果生成出来质量差，再考虑加一个"商品生成提示词模板"字段（仍在 world 实例上 —— 描述类，不算业务数据）。

5. **`realCityRef` 的真实城市清单谁维护？**
   建议：settings 里内置一份「中国 / 世界主要城市」清单，天气 App 自己再加几个映射。

6. **多 AI 是必须的吗？还是先做单 AI + 多个「角色预设」？**
   建议：直接做多 AI 实例，更通用，前期允许只建 1 个。

7. **数据源授权粒度要做到多细？**
   建议：先做「按 App 开关 + 公开/私密两种 scope」，足够覆盖 90% 场景。

8. **★ 概率分布的"惯性"问题**（新增）
   第一版是**纯概率**——每天重新独立抽样，没有"连续性"。要不要做"惯性"——昨天在绒城，今天有 70% 概率仍在原城市、30% 概率迁移？我建议**第一版不做**，等你看到 AI 在城市间乱跳觉得别扭再加。

9. **★ 心情字段类型**（新增）
   第一版用离散字符串（happy/calm/melancholy...）。要不要同时支持三维 PAD（valence/arousal/dominance）？我建议**先不做**，等用户反馈"心情太粗"再加。

10. **★ 当日快照的时区**（新增）
    用本机本地日期，单机 App 没必要处理跨时区。如果未来做云端同步才需要。
    建议：保持本机本地日期。

11. **★ profile 切换时是否给个"已填高级字段被隐藏"的提示？**（新增）
    用户从详细切到简略时，那些 `A` 字段只是 UI 隐藏但**数据还在**。建议两种 UX：
    - 方案 A：静默切换 + 顶部加一行"你有 N 个隐藏字段已设置"小标签；
    - 方案 B：弹一个 modal 列出隐藏字段名单，让用户确认。
    建议方案 A（更轻）。

12. **★ "必须填"在 UI 什么时候卡用户？**（新增）
    现在定的是 `R` 字段在简略模式也要必填。如果用户**故意跳过**呢？
    建议：第一版**允许跳**，但 settings-sdk 在 AI 上下文组装时标记 `incompleteFields: ['pronouns']`，AI 收到一句"以下字段用户未填：[pronouns]，请用合理默认值响应"。不卡用户在主流程上，但 AI 知道自己不知道什么。

13. **★ 标签组的可见性 / 共享范围 / 删除策略**（v0.4 新增）
    - **跨世界观复用**：`scope='global'` 的标签组所有世界观都看到；`scope='world:<id>'` 仅该世界。推荐约定：①「性格 / 种族 / 阵营」类**预设组**用 global；②「京城名流 / 设计圈」这种**自定义组**用 world 级。是否需要更细的 `scope='global+worldOverride'`？建议第一版就 2 档够用。
    - **删除策略**：删一个 world 时，world 级的标签组和标签是**级联删除**还是**孤立保留**？
      建议：**级联删除**（"绒城纪事"没了，"京城名流"也没意义了）。
      但**全局标签组**永不删（即使该组下没有任何 tag）。
    - **同组多标签**：默认一个对象在一个组里**只能选 1 个**标签（互斥）；UI 上"组"是单选。如果用户想多选（如"同时是 F5 和小时代"），需要显式改组定义为 `multi`。建议：第一版只支持"组内单选"，够用。

## 9. 一句话回你之前的问题

> 「用 template 还是什么」

用 **prototype + instance**：
- prototype = 一份模板（用户模板 / AI 模板 / 世界观模板 …），描述有哪些字段。
- instance = 真正存进库里的具体角色。
- 每个具体角色都是某个 prototype 的「填充版」，后续 App 通过 settings-sdk 统一读写，**App 之间靠 instance.id 互相引用**，不需要每个 App 都自己存一份。

我们要做一个单一数据源（SSOT）的设置模块（settings-sdk），作为整个 App 生态的中间层（mediator / service layer）。

它管理原型 + 实例（prototype + instance）模式的实体库（users / ai / worlds / factions / locations / tags / snapshots），所有跨 App 的数据通过它做 CRUD。

实体之间通过引用（reference / foreign key）建立关系，例如 user.locationRef → loc-xxx、ai.feedPermissions.scope → world:xxx。

每个 App 作为插件（plugin）启动时，向 settings-sdk 注册（register）自己提供的数据源（data sources）；AI 在读取数据时由 settings-sdk 根据 ACL（feedPermissions + tagRefs + sentimentMap）做权限过滤，再喂给（inject）AI。

这样所有 App 之间解耦（decoupled），不直接互相调用，新增 App 只需要做一次注册，不需要改老 App。
